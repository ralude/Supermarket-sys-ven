# Sub-fase 9B.10: Configuracion operativa

- **Fase:** [Fase 9B - Perfiles operativos](./README.md)
- **Estado:** Lista para implementación de referencia, con alcance recortado
- **Plan:** [Plan 9B.10](./plan-9b.10-configuracion-operativa.md)
- **Decisión:** administrar los maestros y políticas que ya existen; el catálogo general de
  alícuotas queda diferido.

## Objetivo

Administrar desde la interfaz los datos maestros que hoy solo se siembran al arrancar el nodo:
políticas existentes, métodos de pago, categorías y unidades.

## Contexto

Las tablas existen y se siembran, pero no hay ningun caso de uso que las modifique. Cambiar un
metodo de pago o una alicuota exige tocar la base de datos. AGENTS.md exige que la tasa, el IVA,
el IGTF y cualquier regla fiscal sean configurables y auditables.

## Default de referencia

La tasa IVA continúa en `Product.taxRateBasisPoints`; no se introduce una taxonomía de
alícuotas. `quantityScale` es inmutable después del primer uso. Categorías y unidades usan un
permiso de administración de catálogo existente o su equivalente mínimo; no se crea un sistema
de permisos paralelo. Los cambios dejan auditoría y no reescriben hechos.

## Tareas

- [ ] Definir los casos de uso de administracion con los permisos `config.tax.manage` y
  `config.payment_method.manage`; categorias y unidades se agrupan bajo la administracion de
  catalogo ya existente.
- [ ] Versionar y auditar cambios de políticas fiscales, reutilizando el mecanismo que ya fija
  ADR-0012.
- [ ] Impedir la desactivacion de un metodo de pago o una unidad en uso por un agregado vivo.
- [ ] Publicar los contratos HTTP y la pantalla de configuracion.
- [ ] Probar que un cambio de alicuota no altera retroactivamente un documento ya emitido.

## Criterio de salida

La configuracion operativa existente se administra desde la interfaz, queda versionada cuando
corresponde y no reescribe hechos ya ocurridos. El catálogo futuro de alícuotas no es criterio
de salida de esta sub-fase.
